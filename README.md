# 🔍 Problem Radar

**한국 사용자의 반복 문제 가설을 찾고, 원문으로 검증하는 수동 조사 도구**

> "방법이 없나요?" "매번 이렇게 해야 하나요?" "왜 이런 기능이 없죠?"
> 이런 문장이 사업 아이디어의 원재료다.

---

## 목표

```
정보 10만 개 수집   ❌
문제 1,000개 발견   ❌
좋은 문제 30개 확보  ✅
검증할 문제 5개      ✅
돈 내는 고객 있는 문제 1개  ✅
```

---

## 시스템 구조

```
[수집]
└── 직접 제보·확인한 원문  (Telegram)
         ↓
[수집/정제]
├── 사용자가 제공한 원문·관찰만 수집
├── 불평 시그널 키워드 필터
├── 원문 단위 중복 제거
└── 원문 정규화
         ↓
[AI 분석 — 무료 한 배치 + 가설 정리]
├── 문제 구조화
├── 수집 자료의 한계·신뢰도·검증 질문 추출
├── 점수 산정 (코드에서 0~100 재계산)
└── 동일 문제군 표시 (증거 수는 사람만 기록)
[Problem DB — 사용자가 실행한 수집 가설만 자동 등록]
         ↓
[사람이 독립 원문을 보강]
         ↓
[인터페이스 — Telegram 봇]
├── /collect — 외부 자동 수집 비활성 안내
├── /top     — TOP 10 조회
├── /today   — 오늘 수집 현황
├── /why     — 5 Why 분석
└── /status  — 시스템 상태
```

## 점수 공식

| 항목 | 가중치 |
|------|--------|
| 빈도 (frequency) | 30% |
| 고통 (pain) | 35% |
| 지불의사 (willingness_to_pay) | 35% |

**기본 기준: 한 번에 AI 분석 5건·배치 실패 시 개별 재시도 없음, 사용자가 제공한 직접 제보만 Notion 자동 저장**

규칙 기반 사전 점수와 AI 점수는 후보 선별에만 사용한다. 외부 자동 수집은 비활성화되어 있으며,
Telegram의 `[문제]` 또는 `[제보]`로 제공한 원문·관찰만 AI가 가설로 정리해 Notion에 저장한다.
같은 고객, 상황, 임시방편을 보여 주는 독립 원문 3개(또는 현재 지출과 접근 가능한 고객)가
확인된 항목만 검증 실험으로 넘긴다.

### 1. 패키지 설치

```bash
cd /Users/taenam/business/problem-radar
nvm use
npm install
```

### 2. 환경변수 설정

```bash
cp .env.example .env
```

`.env` 파일 작성:

```env
# Notion — airrouteX와 동일 토큰 사용 가능
NOTION_TOKEN=ntn_...
NOTION_PARENT_PAGE_ID=<Notion 페이지 ID>

# AI — airrouteX와 동일 키 사용 가능
GEMINI_API_KEY=AIza...

# Telegram — airrouteX와 동일 토큰/ID 사용 가능

```

### 3. Notion DB 초기화

```bash
# .env에 NOTION_PARENT_PAGE_ID 설정 후:
node scripts/setup-notion.js

# 출력된 DB ID를 .env에 추가:
# NOTION_PROBLEM_DB_ID=...
# NOTION_WEAPON_DB_ID=...
```

## 데이터 해석 원칙

- Notion 항목은 검증된 사업 기회가 아니라 검증할 문제 가설이다.
- `점수`는 우선순위 정렬용 지표이며 지불의사를 증명하지 않는다.
- 불편을 겪는 사람과 비용을 떠안거나 결제할 사람은 다를 수 있다. 무료 지도·번역 앱·사람의
  도움처럼 강한 대안이 있으면, 개인의 불편만으로 지불 의사를 높게 판단하지 않는다. 대신
  반복 문의·지각·노쇼·직원 대응처럼 운영 손실을 실제로 떠안는 역할이 있는지 확인한다.
- AI 유사군과 URL 수는 증거 수가 아니다. 수집 시 자동 기록되는 `동일 문제 증거수`는
  0이며, 서로 다른 원문에서 고객·상황·현재 대안이 일치하는 것을 사람이 확인했을 때만 올린다.
- 다음 단계는 MVP 개발이 아니라 실제 고객에게 검증 질문을 하고 수동 제안을 하는 것이다.

## 문제 수집함 구조

테이블에서는 `문제`, `상태`, `대상`, `근거 유형`, `동일 문제 증거수`만 보고 후보를 고른다.
`점수`, `수집일`, `원문링크`, `원문ID`는 정렬·중복 방지용으로 숨긴다. 원문 인용, 출처,
현재 해결 방식, 해결 공백, 근거 부족, 검증 질문·제안은 각 항목 페이지 본문에 자동 기록한다.

## 검증 실험실 구조

수집함에서 독립 원문 3개(또는 현재 지출·반복 행동 + 접근 가능한 고객)가 확인된 문제만
검증 실험실로 올린다. 한 번에 검증 후보는 최대 1개만 운영한다.

| 컬럼 | 설명 |
|------|------|
| `실험명` | 실험명 / 가설 |
| `문제` | 문제 수집함 Relation |
| `상태` | 가설 수립 / 실험 진행중 / Go / Pivot / Kill |
| `검증 진입 이유` | **검증 진입 이유** — 왜 수집함에서 여기까지 올라왔는가 (한두 문장) |
| `비용 부담자` | **비용 부담자** — 이 문제가 지속될 때 실제 시간·돈을 부담하는 주체 |
| `실험 방법` | 검증 방법론 (플레이북 1~4 중 선택) |
| `채널` | 실험 채널 |
| `시작일` | 실험 시작일 |
| `성공 기준` | 성공 기준 |
| `실제 결과` | 실제 결과 |
| `학습` | 학습 및 회고 |

`검증 진입 이유`와 `비용 부담자`는 DB 테이블에서 바로 읽힐 때 가치가 있다.
가장 위험한 가설(riskiest assumption)처럼 상세한 사고 과정은 각 실험 페이지 본문에 기록한다.

**검증 흐름:**
```
문제 → 왜 검증하는가(검증 진입 이유) → 누가 비용을 부담하는가(비용 부담자)
→ 어떻게 실험하는가(실험 방법/채널) → 성공 기준
→ 실제 결과 → 학습 → Go / Pivot / Kill
```

## 직접 제보 방법

Telegram에서 다음 형식으로 전송:

```
[문제]
직장인이 매달 복지포인트 사용처를 찾느라 여러 사이트를 돌아다님.

[내 생각]
한곳에서 검색하면 좋을 듯
```

AI가 자동으로 구조화하고 점수를 매겨 Notion에 저장합니다.
